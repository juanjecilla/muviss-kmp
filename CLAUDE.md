# CLAUDE.md

Guidance for Claude Code (and humans) working in the Muviss repo.

## What this is

Muviss is a Kotlin Multiplatform + Compose Multiplatform tracker for movies and TV shows. Package root `com.codingpit.muviss`. Targets: **Android (primary)**, iOS, Desktop (JVM), Web (JS + Wasm), plus a dormant Ktor `:server`. Offline-first, user-focused, no social. Read `CONTEXT.md` for the domain glossary and `docs/adr/` for why things are the way they are.

## Working agreement

**Anything raised in a session and not done in it gets a GitHub issue before the
session ends** — an epic, a bug, or a task. Gaps you scoped out, bugs you found
in code you weren't touching, things you could not verify, traps you worked
around. `docs/EPICS.md`'s backlog carries the issue number for every entry. See
`AGENTS.md` for what a good issue looks like and why this is not optional here:
epics are implemented end to end by one agent and run in parallel, so anything
living only in a session transcript is gone.

## Architecture (see ADR 0004)

Vertical slice per feature, each split into four modules:

```
:feature:<name>:api      public contract — the ONLY module peers may depend on
:feature:<name>:domain   use cases + repository interfaces (internal)
:feature:<name>:data     repo impls + data sources + Koin module (internal)
:feature:<name>:ui       Compose screens + ViewModels + nav (internal)
```

Dependency rule: **`ui → domain ← data`**; cross-feature deps go through the peer's `:api` only. Shared infra:

```
:models             common exported data models (MediaId, MediaSummary, WatchStatus…)
:core:common        AppDispatchers, Koin, coroutines
:core:model         WatchProgress + WatchStatusCalculator (status derivation)
:core:database      SQLDelight schema + drivers (expect/actual)
:core:network       Ktor client + MetadataProvider + TmdbProvider
:core:sync          SyncBackend seam + SyncEngine + Supabase impl (ADR 0009)
:core:billing       EntitlementProvider seam; no store SDK yet (ADR 0018)
:core:designsystem  Compose theme + shared components (PosterImage, MuvissIcons)
:app:shared         app shell: MuvissApp() — Koin start, theme, NavHost, bottom bar
:app:{androidApp,desktopApp,webApp,iosApp}   thin platform hosts
:server             Ktor, dormant (not deployed)
```

DI is **Koin**. Each module contributes a Koin module; `app/shared/.../di/AppModules.kt` assembles them. Navigation is the official **Navigation Compose** with `@Serializable` type-safe routes; each feature `:ui` exposes a `NavGraphBuilder.<name>Section()` extension and a `<Name>Route`.

Build boilerplate is in the included build `build-logic/`: apply `id("muviss.kmp.library")` (non-UI modules) or `id("muviss.kmp.compose")` (UI modules). The Android namespace is derived from the module path automatically.

## Adding a feature (copy the search slice)

1. Create `:feature:<name>:{api,domain,data,ui}` mirroring `feature/search/*` (all six existing slices are real implementations).
2. Register the modules in `settings.gradle.kts` (the `listOf(...)` loop) and add the feature name.
3. Add the feature's Koin modules to `AppModules.kt`, and its `Route` + `Section` to `MuvissApp.kt`.
4. Depend on a peer only via its `:api`.

## Domain rules that bite (see ADR 0005)

`WatchProgress` (episode ticks) is the source of truth; `WatchStatus` is **derived** by `WatchStatusCalculator` — never store status independently. Rewatches live in `episodePlay` (one row per viewing, ADR 0011), written in the same transaction as `episodeProgress.seen`, never separately — `seen` stays the stored column sync and status derivation key off.

`episodePlay` now syncs too (ADR 0013), which changed its shape: its primary key is the **derived** `TEXT` id `episodeId@watchedAtEpochMs` (a per-device AUTOINCREMENT could never be a sync key), writes go through `upsert` with the id composed by `SqlDelightProgressRepository.playId`, and its deletes are **soft**. Every read of that table must filter `AND deleted = 0` — forget it and you silently inflate a play count on the detail screen or add days the user never watched to the profile watch-streak. Last-write-wins cannot express a hard delete: a physically removed row has no timestamp left to compare, so the other device's copy just gets pushed back and "clear watch history" undoes itself.

**Any bulk "mark seen" ticks aired episodes only.** `markSeasonAiredSeen`/`markShowAiredSeen` filter through `EpisodeOrdering.airedBy`. Ticking an unaired episode pushes `seenEpisodes` past `airedEpisodes`, and `WatchProgress`'s `require(seenEpisodes <= airedEpisodes)` *throws* — the Library screen crashes the next time it derives that title's status. This is the same trap the triage note below describes, reached from the detail screen instead. TV: NotStarted → Watching → Watched (all aired, ongoing) → Finished (all seen, ended). Movies: NotStarted → Watched. `Favorite` is an independent flag.

The **`episode` table is cache, not user data** (ADR 0015). It holds what TMDB says a show contains, so it has no `isDirty`/`updatedAt`/soft delete, is absent from `SyncChangeSet` and from the data export, and a refetch replaces a title's rows wholesale. `SyncChangeSetShapeTest` and `ExportShapeTest` fail if that changes by accident. It is what makes "next unseen episode" answerable offline — `EpisodeCatalogCache` reads it before the network — and it ships with **no backfill**, so it is empty on every upgraded install until the app runs once.

**"What do I watch next" has one implementation**: `WatchNextUseCase` (`feature/progress/domain`), behind `ProgressApi.observeWatchNext()`. The Progress tab and both home-screen widgets are renderings of it. Don't rebuild the collection × catalog × ticks join in a new surface.

**A Snooze is not a verdict** (EPIC 42, ADR 0023). `triageSnooze` is its own table, deliberately not a fifth `TriageVerdict`: an unknown verdict makes `TriageVerdict.fromStored` return null, so `SqlDelightTriageDecisionRepository` drops the row from every read while `selectDecidedIds` still counts it — an older build or a peer device would exclude the title from its deck forever with nothing able to show or undo it. Its deletes are **soft** and every read must filter `AND deleted = 0`, the `episodePlay` lesson again. It carries the whole card (`title`/`year`/`posterUrl`/`overview`) because `MetadataProvider` has no `summary(id)`, only `details(id)` — which for a show is `1 + ceil(seasons / 20)` requests that bypass `HttpCache`; the cost is that `overview` is frozen in the TMDB language active when it was snoozed. Due snoozes re-enter through `DeckLoader` as a **second source**, capped at `MAX_SNOOZES_PER_BATCH` and never in the first slot, because `LoadDeckUseCase` could otherwise only ever *exclude* and `/discover` will not return a three-month-old title on page 1. The snooze affordance is a **button on the card**, not a fifth column: `VerdictButtonRow`'s KDoc records that four labels already overflowed a 1080px phone. Long press and `S` are accelerators — a mouse has neither, so the button is what makes it work on all six targets.

Triage (ADR 0010) obeys the same rule: a `CaughtUp` verdict does not write a status, it writes ticks — `ProgressApi.markAllAiredSeen`, **not** `markPreviousSeen`. The difference matters: `markPreviousSeen` walks a contiguous prefix and would also tick anything unaired positioned before the target (an undated season-0 special is the common case), and `WatchProgress`'s `require(seenEpisodes <= airedEpisodes)` *throws* — so reading the library's own status would crash. `TriageDecision` is a log of intent, never a status, and deliberately outlives the `CollectionEntry` it created.

## Setup gotchas

- **TMDB credentials**: put `TMDB_READ_TOKEN=<v4 read token>` and/or `TMDB_API_KEY=<v3 key>` in `local.properties` (gitignored). Both are baked into the generated `MuvissBuildConfig` (see ADR 0007). `TmdbProvider` sends the token as `Authorization: Bearer` when it is set and falls back to the v3 key as the `api_key` query parameter when it is not — the token is the one that keeps a credential out of URLs, so prefer it. Without either, search fails with `MetadataError.Unauthorized` at runtime but everything still builds.
- **Network errors are `MetadataError`, never exception text** (EPIC 27). `TmdbProvider` only ever throws `MetadataError` (in `:models`: `RateLimited`/`Unauthorized`/`NotFound`/`Offline`/`Unknown`), with fixed text and **no `cause`** — Ktor's timeout messages embed the full request URL, which for the v3 fallback contains the key, and Sentry walks the cause chain. View models render `e.toUserMessage(FALLBACK)`; **never `e.message`** in state, a snackbar, or a report. The TMDB policy (`expectSuccess`, validator, `HttpRequestRetry`, `HttpCache`) lives on a client *derived* from the shared one in `TmdbProvider` (`HttpClient.config` reuses the engine); it must not move onto the base client, because the Supabase sync client shares that and reads non-2xx statuses itself. Likewise no default header on the base client — it would ride to every host. The Ktor plugins (retry, cache, validator) are engine-independent and so behave identically on OkHttp, Darwin and Js; `HttpCache` is **in-memory only** (gone with the process), `UserAgent` is not installed on web (not CORS-safelisted, browsers may drop it), and Coil's 100 MB disk cache is a no-op on web.
- **TV detail costs `1 + ceil(seasons / 20)` requests**, via `append_to_response=season/1,...` (TMDB caps appended items at 20). A season missing from the appended response falls back to its own `/tv/{id}/season/{n}`. Title *details* deliberately bypass `HttpCache` (a `max-age` would hand the library refresh and the new-episode check their own stale answer). `TmdbProvider` also caps in-flight requests at 4 for every caller at once; bulk refreshes (`mapBounded`, `REFRESH_CONCURRENCY`) add title-level concurrency on top.
- **Sync is gated twice and off by default; automatic sync a third time** (EPIC 40, ADR 0021) (ADR 0018, `docs/SYNC.md`). To run it locally you need all four of `SYNC_ENABLED=true`, `SYNC_ENTITLEMENT_OVERRIDE=true`, `SUPABASE_URL` and `SUPABASE_ANON_KEY` in `local.properties`; add `SYNC_BACKGROUND_ENABLED=true` to get the "Sync automatically" switch on Profile (it means nothing without `SYNC_ENABLED`). `SYNC_ENABLED` + the keys are the **build** gate (`SyncAvailability` → `NoOpSyncBackend`, and the profile screen renders no sync row at all); `SYNC_ENTITLEMENT_OVERRIDE` is the **entitlement** gate (`:core:billing` binds `AlwaysEntitledProvider` instead of the fail-closed `NoEntitlementProvider`, so `SyncEngine.syncNow()` stops returning `NotEntitled`). None of the four is set in CI or release builds — that absence is what keeps sync out of production. The two gates present oppositely on purpose: `SyncAccountState.Unavailable` hides the row, `Locked` shows it with a paywall. Note that `local.properties` does **not** follow you into a git worktree.
- **Sync sign-in is OAuth over a custom scheme — except on desktop** (ADR 0014, replacing ADR 0009's email one-time codes — Supabase's free tier refuses to edit the email templates, and its stock ones send a link where the app wanted a typed code). The redirect `muviss://auth-callback` must stay byte-identical in **three** places that cannot reference each other: `OAUTH_REDIRECT_URI` in `:core:sync`, the `auth-callback` intent filter in `app/androidApp`'s manifest (and iOS's `CFBundleURLSchemes`), and `additional_redirect_urls` in `supabase/config.toml` (applied with `supabase config push`). **Desktop is a fourth place and a different value**: it owns no scheme that survives `./gradlew run`, so it binds a loopback server on 53682/3/4 and those three URLs must be on the allow-list too (ADR 0017; `LoopbackRedirectServer.PORTS` is the list). The redirect URI varies through a Koin-bound `OAuthRedirectTarget` rather than an `expect val` — `:core:sync`'s whole test suite is `jvmTest`, so a JVM actual would silently rewrite what every sync test asserts about `redirect_to`. And know *when* an allow-list drift bites: GoTrue's `/authorize` accepts any `redirect_to` and 302s to the provider regardless, so the flow starts normally and only the redirect *back* is refused — it presents as the browser landing on `site_url` with "cannot connect to the server", long after the point you changed. Sign-in completes in `MuvissApp`, not the profile screen — the redirect can arrive on a cold start, long after `ProfileViewModel` is gone, so the signed-in state propagates through `SyncBackend.session` instead of a return value. Flow is PKCE; `sha256`/`secureRandomBytes` are `expect`/`actual`, real on android/jvm only.
- **Sync correctness rules that bite (EPIC 39, ADR 0020, `docs/SYNC.md` "How a sync cycle works").** The pull cursor is a **server-assigned `server_seq`, one per table** (`syncCursor`), never a client timestamp; a pull pages until an **empty** page because Supabase's `max_rows` truncates silently; and `SyncBackend.pull(after, onPage)` streams pages with an opaque `SyncCursor`. Push bodies **must carry `null` explicitly** — `SupabasePostgrestClient` owns its `Json` with `explicitNulls = true`, because PostgREST's merge-duplicates upsert never writes a key absent from every object, so `muvissJson`'s `explicitNulls = false` can never clear a column; don't route sync bodies through the shared client's content negotiation. Every `clearDirty` is `AND updatedAtEpochMs = :pushedAt`, so an edit made mid-push stays dirty. **A snapshot refresh is not a synced write**: use `CollectionRepository.refreshSnapshot` (no stamp, no dirty, live rows only) for provider data and `upsertSnapshot` only for "add to library"; anything that re-stamps a row on a Library visit lets a stale device beat another device's real edit. A pulled row replaces a local one when the local row is clean or the pulled one is newer than unsent edits, and a winning `collectionEntry` takes **user fields only**. After a pull the engine raises `airedEpisodes` to the ticked count (the `WatchProgress` invariant is unchanged) and reconciles `seen` against `episodePlay`; both run inside `RemoteApplier`, and reconciliation cannot run per page because the two tables arrive separately. `syncState.ownerAccountId` gates whose library this is: a different account gives `SyncOutcome.AccountChanged` until `resolveAccountChange`. `FakeSupabaseServer` (`:core:testing`) is the sync test double — it models PostgREST and the triggers by hand, so keep it and `supabase/migrations` in step; its assumptions are checked live only by `scripts/sync/verify-*.sh` (issue #88).
- **Never gate a paid feature in the UI layer alone.** `MuvissApp`'s `AutoSyncOnForeground` reaches the engine on every `ON_START`/`ON_RESUME` (through `SyncCoordinator.onForeground()`), bypassing the profile screen entirely — which is why the `EntitlementGate` check, and since EPIC 40 the build flag and the switch (`AutoSyncPolicy`), live inside `SyncEngine.syncNow(trigger)`. `:core:sync` never depends on `:core:billing`; the two are joined in `app/shared/.../di/BillingSyncBridge.kt`, which must stay **after** `syncModule` in `AppModules.kt` because both bind `EntitlementGate` and Koin's last binding wins.
- **Automatic sync rules that bite (EPIC 40, ADR 0021, `docs/SYNC.md` "Automatic sync").** `SyncEngine.syncNow(trigger: SyncTrigger)` is the only place the build flag (`SyncAvailability.isBackgroundAvailable`), the per-device switch (`FeatureFlags.syncAutomatically`, `appSettings`, default off), the session and the entitlement are checked; every automatic trigger (`Foreground | Change | Periodic | Resume`) that fails returns `SyncOutcome.Disabled` having touched nothing, and `Manual` skips the first two only. Add a trigger by asking the engine, never by checking the switch yourself. `SyncCoordinator` (5 s debounce, one change run per 30 s, backoff capped at 15 min, 60 s foreground skip) owns *when*, the policy owns *whether*. **`FeatureFlags` has a fake in four test suites** (`SettingsViewModelTest`, `TriageUiTestFixtures`, profile:data's `SyncRepositoryFixtures`, and `CrashReportsSettingTest`'s `NoFlags`): a new flag breaks all four. This said *three* until EPIC 42 counted them. **`syncCursor` holds one row that is not a cursor**, `_lastFullPullAt` (the weekly full pull); a test that reads the table must skip names starting with `_`, and `loadCursors` already does. **`SyncWorker` needs its `-keep` rule** in `app/androidApp/proguard-rules.pro`: WorkManager instantiates it by class name and only a minified build shows the `ClassNotFoundException`. **`syncState.lastError` is `REASON: text`**, read back with `SyncFailureReason.fromStored`; copy comes from `SyncCopy`, never from an exception's message. Two test traps: `runTest` **auto-advances virtual time whenever its body suspends**, so waiting for a real-thread reply (the `FakeSupabaseServer` mock engine) with `withContext(Dispatchers.Default) { delay() }` silently fires every pending debounce; block with `Thread.sleep` instead. And **two Koin graphs built from the same `appModules` share their singletons** (the module objects keep their instances), so two "devices" in one test need another mechanism (`FakeSupabaseServer.seed`).
- **RevenueCat is not wired up yet** and `purchases-kmp` publishes **Android + iOS artifacts only** — putting it in a `commonMain` breaks `compileKotlinWasmJs` for every downstream module, the same trap as the `:models` serialization note below. It belongs in `:core:billing`'s `androidMain`/`iosMain`. The paywall already has the matching seam (`feature/profile/ui`'s `rememberPaywallPresenter`, six actuals, all currently `HandRolledPaywall`). Also check any new billing dependency against `app/androidApp/build.gradle.kts`'s `licensee` allow-list (`Apache-2.0`/`MIT` only) before adding it.
- **Release signing / Sentry**: `RELEASE_STORE_FILE`/`RELEASE_STORE_PASSWORD`/`RELEASE_KEY_ALIAS`/`RELEASE_KEY_PASSWORD` and `SENTRY_DSN` are all optional, read from `local.properties` or env vars the same way as the TMDB key. Without them, `:app:androidApp:assembleRelease` falls back to debug signing and crash reporting no-ops. See `docs/RELEASING.md`.
- **Desktop starts Koin before Compose**, like Android and iOS, because the loopback sign-in server has to be *in* the graph for `CoreSyncRepository` to resolve it. That means `DatabaseDriverFactory` must be bound in `Main.kt`'s module too: `MuvissApp()`'s `KoinApplication` reuses a running global instance rather than starting a second one, so its own `platformDatabaseModule` never applies once one exists. Also note `nativeDistributions { modules(...) }` carries `jdk.httpserver` for that server — same invisible-until-runtime hazard as `java.sql`, and CI's per-PR `packageDistributionForCurrentOS` + packaged-binary smoke launch exists to catch the class of breakage that a compile cannot (a *missing* module is still not caught; issue #43).
- **Desktop DB**: `:core:database`'s JVM driver is file-backed (`DatabaseFactory.jvm.kt`), one SQLite file at the OS-appropriate app-data dir — `~/Library/Application Support/Muviss` (macOS), `%APPDATA%\Muviss` (Windows), `$XDG_DATA_HOME/Muviss` or `~/.local/share/Muviss` (Linux) — created on first run, opened and migrated forward on later ones. jvmTest suites bypass it entirely (they build `JdbcSqliteDriver.IN_MEMORY` + `Schema.create` directly); `DatabaseFactoryJvmTest` covers the file/migrate-on-open logic itself against a temp dir.
- **Migrations**: the schema is at **version 13** (`1.sqm`..`12.sqm`, fixture `13.db`). `9.sqm` is EPIC 39's (sync cursors and owner), `10.sqm` is EPIC 26's (`appSettings.crashReportsEnabled`), `11.sqm` is EPIC 41's (co-watch) and `12.sqm` is EPIC 42's (`triageSnooze` plus three `appSettings` columns). **EPIC 28 (#70) still claims `11.sqm` on an unmerged branch and must renumber to `13.sqm`.** `docs/EPICS.md` records how the numbers actually landed, and the number a branch takes is whatever is free when it merges — `verifyMigrations` cannot see a collision, so re-check that line before adding a `.sqm`. It grew additively with no `.sqm` files through EPICs 0-8 — every install so far always created the DB fresh, there was never an upgrade path. Those four files **as they stand today are schema version 1**, baselined with no migration file needed to represent it (see `core/database/build.gradle.kts`). From here on, any change to a `CREATE TABLE` that existing installs need to pick up without losing data ships as a new `<version>.sqm` file alongside the `.sq` change. Since EPIC 24 the `.sqm` chain covers **web** too: `SchemaEnsuringDriver` reads `PRAGMA user_version` off the restored snapshot and creates/migrates/leaves alone, where it used to call `awaitCreate` unconditionally because web's DB was always empty. `verifyMigrations` is on, wired into `:core:database:check` (and CI) automatically by the SQLDelight plugin — it fails the build if the `.sqm` chain doesn't reproduce what the `.sq` files declare, against the checked-in schema fixture `core/database/src/commonMain/sqldelight/databases/1.db` (regenerate it via `generateCommonMainMuvissDatabaseSchema` if you ever need to, though normally you'd add a `2.db` for the next version instead of touching this one).
- **iOS DB path**: `muviss.db` lives in the **`group.com.codingpit.muviss` App Group container**, not `NSDocumentDirectory` (ADR 0016) — a WidgetKit extension is a separate process and could not otherwise see it. `DatabaseFactory.ios.kt` moves a pre-v9 database there once, on first open, taking the `-wal`/`-shm` sidecars with it, and **falls back to the old Documents path when the entitlement is missing** — which is every build until `TEAM_ID` and the App Group are set up by hand (docs/RELEASING.md §11). Don't "simplify" that fallback away: without it a fresh clone crashes on launch.
- **Glance reads its data *inside* the composition.** `provideContent` composes and then suspends for the life of the session, so a later `update()` recomposes the composition it already has — it never re-enters `provideGlance`. Anything read before `provideContent` is frozen for as long as the session lives, which shipped once as a widget that wrote a tick and then went on displaying the episode it had just ticked. `MuvissWidget` collects `observeWatchNext()` with `collectAsState` and reads the Undo marker via `currentState<Preferences>()`; the `WidgetRefresher` push is what wakes a *stopped* session, not what updates a live one. Only running it on a device catches this — the state mapper's unit tests all passed.
- **Crash reporting starts first, before Koin, and reads its consent from the database on a driver of its own — off the calling thread (#124).** Every host calls `MuvissCrashReporting.start(DatabaseDriverFactory)` (`:app:shared`) as its first line — `MuvissApplication.onCreate`, desktop's `main`, `IosAppStartup.start` — because a crash while the graph is built, or in a `NewEpisodesWorker` cold start, is the one you most need to see. `start` inits the SDK *synchronously* with `CrashReportsConsent.DEFAULT` (on) — no database touched yet — then reads the real stored choice on a background dispatcher and applies it within milliseconds via `CrashReporter.setEnabled`, the same live gate the Settings toggle uses; doing that read inline would put `DatabaseDriverFactory.create()`'s create-or-migrate (synchronous on Android/iOS/JVM) on the caller's thread, the app's main thread on Android, with no ANR budget to spare. `MuvissApp()`'s call is only a guard: `CrashReporter.init` is idempotent, only the call that starts the SDK sets consent, and the guard starts with reporting *off*. Consent is a runtime gate in `beforeSend`, so a new event path must go through `CrashReporter`/the SDK's own handlers, never a second `Sentry.init`. Every `viewModelScope` launches through `launchReporting` / `launchInReporting` (`:core:common`), which reports and does not rethrow; a bare `viewModelScope.launch` reintroduces the silent-or-fatal split — enforced repo-wide by a detekt rule (`ForbiddenViewModelScopeLaunch`, the top-level `:detekt-rules` module — a plain Kotlin/JVM module wired into every other module's `detektPlugins` config from the root `build.gradle.kts`, not `build-logic`, which is a plugin-management-only included build). `release`/`dist` must equal what the Sentry Gradle plugin stamps on the R8 mapping (`MuvissCrashReporting.releaseOf`), or traces stay obfuscated. The Sentry `beforeSend`/scrubbing mapping itself lives once, in `:core:common`'s `sentryMain` source set (an extended Kotlin hierarchy template, shared by android+jvm+ios — see `core/common/build.gradle.kts`), not duplicated per platform actual. **Web has a reporter too (#83)**, but a different one: `sentry-kotlin-multiplatform` publishes no-op stubs for js/wasmJs, so `WebCrashBackend` (`core/common/src/webMain/.../crash/`) drives Sentry's browser SDK directly instead, loaded from Sentry's CDN (`browser.sentry-cdn.com`) only when a DSN is configured — never on the default unconfigured build, same as the other three. The CDN script is plain global (`window.Sentry`), not an npm import, specifically so `SentryJs`'s `js(...)`-bodied actuals (`SentryJs.js.kt`/`SentryJs.wasmJs.kt`, byte-for-byte identical, the same tolerance `DatabaseDriverFactory`'s web actuals already accept) don't need `@JsModule`, which Kotlin/Wasm's JS interop does not support. Web has no pre-Koin startup hook (`app/webApp/.../Main.kt` just composes `MuvissApp()`), so unlike the other three platforms, `MuvissApp()`'s `followSettings()` call is not just a guard there — it is the only place web's stored consent ever gets applied, which is why it moved inside the `KoinApplication` content lambda (Koin has to exist first) rather than sitting next to `ensureStarted()`.
- **Home-screen widgets**: Android's is Glance in `:app:androidApp/.../widget` (a `GlanceAppWidgetReceiver` runs in the app process, so `KoinComponent` + `by inject()` works exactly as it does for `NewEpisodesWorker`); iOS's is SwiftUI under `app/iosApp/MuvissWidget`, reaching Kotlin only through `IosWidgetBridge` (flat strings — the `Shared` framework has no `export(...)`, so widening it would put the whole progress contract into Swift's headers). Glance renders through the app-widget host rather than Skiko, so `runComposeUiTest` cannot see it: the testable part is the pure `watchNextWidgetUi` mapper, and the composition itself is verified on a device. Colour comes from `MuvissPalette` via `muvissColorScheme()` — `MuvissTheme` is a `MaterialTheme` wrapper and cannot wrap a Glance tree.
- **Peer `:api` cycles are real and only the graph shows them.** Collection's repository needs `ProgressApi` to derive `WatchStatus`, so anything on `ProgressApi` that needs `CollectionApi` closes a construction cycle Koin follows until the stack overflows — on the first frame, before anything renders. `WatchNextUseCase`/`RefreshWatchNextCatalogsUseCase` therefore take `() -> CollectionApi`, resolved per call. `:app:shared`'s `AppGraphTest` assembles the real `appModules` and resolves every contract in both orders; it is the only test in the repo that would have caught it (`Module.verify()` would not — it checks definitions without instantiating).
- **`WidgetRefresher`**: `:core:common/.../widget/`, called from `SqlDelightProgressRepository` after every committed write — that repository is the one place every progress mutation funnels through, which is why the call lives there. `AppWidgets` resolves its delegate **per call**, not per Koin binding, because the platform hosts install theirs (`MuvissApplication.onCreate`, `IosAppStartup.start`) later than the graph that already handed the repository one. WidgetKit is Swift-only with no Objective-C surface, so iOS's reload is passed in from `AppDelegate` rather than called from Kotlin.
- **Web + DB**: `:core:database`'s JS/Wasm driver (`DatabaseFactory.web.kt`, shared via `src/webMain`) persists for real now (EPIC 13) — SQLDelight's `web-worker-driver` running `@cashapp/sqldelight-sqljs-worker` (SQL.js in a Web Worker). `generateAsync` is on schema-wide; every generated mutation is `suspend` on every platform, Android/iOS/JVM bridge back to their sync drivers via `MuvissDatabase.Schema.synchronous()` (from `app.cash.sqldelight:async-extensions`) so nothing about their behavior changed. Web persistence is **durable** since EPIC 24 (ADR 0008's 2026-09-04 amendment): the worker is **ours** (`core/database/src/webWorker`, a fork of `@cashapp/sqldelight-sqljs-worker`, which hard-codes `new SQL.Database()` and exposes no persistence seam at all), and it restores an IndexedDB snapshot on open and re-exports the whole DB ~500ms after the last committed write, plus a `flush` on `pagehide`. Two consequences worth knowing before you touch it. **It must stay a local npm package**, not a file in resources — `new URL("muviss-sqljs-worker/...", import.meta.url)` has to resolve through `node_modules` or webpack copies it verbatim without bundling its own `sql.js` import, and the symptom is a worker that loads with a 200 and hangs forever with no console error. And **only one tab persists**: the worker holds a Web Lock for the tab's lifetime, because two tabs are two in-memory DBs over one IndexedDB slot and the loser would otherwise overwrite the winner wholesale. Also note `{ type: "module" }` in the `js(...)` snippet is shape, not behaviour — webpack rewrites it to `{type: void 0}` and emits a *classic* worker, which is why the worker's `typeof importScripts` guard is what installs its handler. Getting the worker to actually load required two webpack fixes documented in `docs/adr/0008-...md`'s 2026-07-16 amendment (`app/webApp/webpack.config.d/copy-sqljs-wasm.js`): the `new Worker(new URL(...))` construction has to be one untouched `js(...)` string or webpack's native worker-chunking never triggers, and `sql.js`'s dual Node/browser loader needs `fs`/`path`/`crypto` resolve fallbacks disabled.
- **Data export**: real per-platform impls — Android's system share sheet, iOS's `UIActivityViewController` (writes to a temp file first so the receiving app sees a proper `.json`), JVM's native `FileDialog` (SAVE mode), web's `<a download>` + object-URL Blob (`DataExporter.js.kt` / `DataExporter.wasmJs.kt` — can't share one `webMain` file because `org.w3c.files.Blob`'s Kotlin interop type differs between the two: `Array<Any?>` on `js`, `JsArray<JsAny?>` on `wasmJs`). Now that web persistence is real (see above), web's exporter has actual data to hand off too.
- **Compose UI tests**: `runComposeUiTest` (`org.jetbrains.compose.ui:ui-test`) renders through Skiko, whose native binary ships in the desktop artifact rather than in `ui-test` — so Compose tests only execute on `jvmTest`. Both dependencies are wired centrally in `muviss.kmp.compose` (`commonTest` gets `compose.uiTest`, `jvmTest` gets `compose.desktop.currentOs`); a `:ui` module needs nothing in its own build file. Two traps that cost time in `:feature:triage:ui`: a focus target inside `Scaffold` cannot take focus from a `LaunchedEffect` (Scaffold subcomposes, so the node is not placed yet — put the `focusRequester`/`onPreviewKeyEvent` on a `Box` *around* the Scaffold), and `PosterImage` renders the title as its no-artwork fallback, so matching a card by title finds two nodes — match the tag (`TRIAGE_CARD_TAG`) instead. A third: a `testTag` applied *outside* a `graphicsLayer` does not move with its `translationX` — the semantics node's `positionInRoot` never walks through the layer — so `getUnclippedBoundsInRoot()` on `TRIAGE_CARD_TAG` reports the card at rest all through a swipe. Tag a descendant of the layer to assert on-screen motion (`TRIAGE_CARD_FACE_TAG`).
- **Test names in `commonTest`**: Kotlin/Native rejects punctuation in backticked function names — a comma is enough to fail `compileTestKotlinIosArm64` with `Name contains illegal characters: ","`. JVM accepts them, so `:module:jvmTest` stays green and only `./gradlew build` catches it, nine minutes in. Anything under `commonTest` uses `underscore_case` (see `WatchStreakCalculatorTest`); backticked sentences are fine in `jvmTest`-only suites, which most `:data` modules' tests are.
- **Screenshot tests**: `:core:testing` holds a hand-rolled golden-image harness — `assertMatchesGolden(name)` over Skiko, so no Roborazzi/Paparazzi dependency. Goldens live in each module's `src/jvmTest/resources/screenshots/`; record with `./gradlew <module>:jvmTest -Precord` (or `MUVISS_RECORD_GOLDENS=1`) and commit the PNGs. Comparison is **not** byte-exact: a pixel counts as changed once a channel moves more than 8/255, and a test fails once more than 0.5% of pixels have. That tolerance exists for antialiasing drift between macOS and Ubuntu CI — font *selection* is already pinned, because `MuvissTheme` sets the bundled Schibsted Grotesk on every text style, so no host font ever participates. **The theme is not pinned for you**: `MuvissTheme`'s `darkTheme` defaults to `isSystemInDarkTheme()`, which on desktop is the *host machine's* setting — a golden recorded on a Mac in dark mode fails on CI with 99.99% of pixels moved. Every golden test passes `darkTheme` explicitly. Wrap content in `GoldenSurface` (a fixed 412x892dp opaque frame) so the image is the same size on every machine; on a mismatch the actual and a magenta-marked diff are written under `$TMPDIR/muviss-goldens/<name>/`.
- **Window insets**: the app is edge-to-edge (`enableEdgeToEdge()`, and `targetSdk 36` forces it), but the shared root is `NavigationSuiteScaffold`, whose content lambda yields no `PaddingValues` and which takes no `contentWindowInsets` — so nothing insets content unless something asks. `ScreenInsets` (`:core:designsystem/.../layout/ScreenInsets.kt`) is that one place, wrapping the `NavHost` in `MuvissApp.kt`. It applies `safeDrawing.only(Top + Horizontal)`: `safeDrawing` for `displayCutout`, and no bottom because the nav bar/rail inset themselves. `windowInsetsPadding` *consumes* what it applies, so a descendant `Scaffold` does not double-pad. Its `insets` parameter exists because **Skiko reports zero insets** — a desktop screenshot of an inset bug is identical before and after the fix, so tests pass `TestSafeAreaInsets` instead. That verifies the layout responds to a safe area; whether Android reports the cutout is only observable on a device.
- **UI copy is localized (EPIC 31, #74): English in `values/`, Spanish in `values-es/`.** Each UI module's strings live in its own `src/commonMain/composeResources/values*/strings.xml`; `muviss.kmp.compose` gives it an **internal** `Res` in `com.codingpit.muviss.<module path>.generated.resources`, so never reach for a peer's `Res` — copy that crosses a module boundary, or leaves a view model, travels as `UiText` (`:core:designsystem/.../text/UiText.kt`), resolved with `resolve()` in composition or `resolveAsync()` outside one. Plurals are `<plurals>` + `UiText.Plural`, never `if (n == 1)`. The detekt rule `HardcodedUiCopy` (`:detekt-rules`) flags literals passed to `Text(...)` and copy-bearing named arguments in `commonMain`; `config/detekt/detekt.yml` excludes the feature `:ui` modules not migrated yet — a ratchet, each migration PR deletes its own line. Positional constructor args are invisible to it (the nav labels were), so grep a module for `"[A-Z][a-z]` before calling it done. Three traps: **Android packages Compose Resources only because `muviss.kmp.compose` sets `androidResources.enable = true`** — without it the APK has no strings *and no fonts*, JVM tests pass, and the app throws `MissingResourceException` on launch (Schibsted Grotesk silently never shipped on Android before EPIC 31); **test JVMs are pinned to `en-US`** in the same convention, because a Spanish-locale host otherwise renders "Reintentar" where tests assert "Retry"; and `MuvissDestination.key` (stable, unshown) is what desktop's shortcuts are keyed by, not the now-localized `label`. Verify a locale on Android without touching the device language: `adb shell cmd locale set-app-locales com.codingpit.muviss --locales es-ES` (empty `--locales ""` resets).
- **Bottom-nav icons**: `material-icons-extended` still isn't published for this Compose version — the five nav glyphs are hand-bundled `ImageVector`s in `:core:designsystem/.../icon/MuvissIcons.kt` (parsed from Material Design SVG path data with `PathParser`) rather than pulled from that artifact.
- **OSS licenses**: `app.cash.licensee` (applied to `:app:androidApp` only) validates dependency licenses at build time and is config-cache-compatible; the Settings > About > Licenses screen instead reads a generated-once, checked-in list (`feature/settings/domain/.../OssLicenses.kt`) — see docs/RELEASING.md item 6 for why the two aren't wired together live.
- Bleeding-edge toolchain (Kotlin 2.4, AGP 9, Gradle 9.1). Prefer editing `gradle/libs.versions.toml` for versions; verify new libs publish for `wasm-js` before adding them.
- **`:models`'s serialization dependency is `api`, not `implementation`** (see `models/build.gradle.kts`) — it must stay that way. `:models`'s `@Serializable` enums (`MediaType`, `WatchStatus`, `ProductionStatus`...) expose their generated `Companion` as a `KSerializer` supertype; the JVM backend tolerates a consumer not having `kotlinx-serialization-core` on its own compile classpath (lazy class-file resolution), but the JS/Wasm klib backend fully resolves that supertype at compile time for every downstream module, so scoping it to `implementation` breaks `compileKotlinJs`/`compileKotlinWasmJs` for any module that merely references one of these enums (e.g. `:core:model`'s `WatchStatusCalculator` did — this was issue #10).
