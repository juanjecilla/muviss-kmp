# Sync: what stands between today and production

Issue #725 (checklist). Assessment of 2026-11-09; re-verify before acting on a row.

## Is RevenueCat ready?
No part of it exists in the repository. There is no RevenueCat dependency in any build file or `libs.versions.toml`; `:core:billing` binds `AlwaysEntitledProvider` (when `SYNC_ENTITLEMENT_OVERRIDE` is set) or the fail-closed `NoEntitlementProvider`; the paywall is `HandRolledPaywall` on all six targets; ADR 0019 is accepted and not implemented. Whether the RevenueCat dashboard, Play subscription and App Store product exist cannot be read from the repo: that is the owner's checklist below (#66).

## Suggested order
1. Owner: RevenueCat project, entitlement id **`sync`** (the #283 webhook, `SYNC_ENTITLEMENT_ID`, ignores events for any other id, so a different choice fails the purchase-to-sync check unless the webhook changes too), offering, Play subscription, App Store product, webhook secret (#66). Nothing in code can be tested against real stores before this.
2. Dev Supabase: enable the access-token hook (#282), merge-test #283's migrations on dev only.
3. `RevenueCatEntitlementProvider` in `:core:billing` `androidMain`/`iosMain` only. `purchases-kmp` publishes Android + iOS artifacts, and a `commonMain` dependency breaks `compileKotlinWasmJs` for every downstream module (CLAUDE.md). Check licensee's Apache-2.0/MIT allow-list first.
4. Real paywall presenter behind `rememberPaywallPresenter`; desktop can hold an entitlement but not sell one; **web is blocked** because OAuth sign-in throws before it starts (#46), so a web user cannot obtain the account entitlement until #46 lands.
5. Client entitlement states and account deletion (#279, #285, #287), then the public deletion page.
6. Live checks on dev: token refresh past expiry, fresh-install restore and the Android upgrade (`docs/SYNC.md` "Still open"; #100 and #114 cover only part of it), against the real stores' sandbox where the check needs one.
7. **Ship the schema first.** Before merging #283, compare hosted dev's migration history with the final migration files: the original versions were applied to dev under their first timestamps, and `supabase db push` fails when the recorded versions differ from the files. Confirm the schema is the same, then reconcile (`supabase migration repair`, dev only). A release that carries #283's migrations to prod through the release train (re-timestamped, #727) with sync still compiled out. The gate fails closed, and no released client uses sync, so nobody is affected; it is what lets step 8 exist.
8. **Production entitlement rollout** (#282). This step creates sandbox entitlement rows on prod, which `docs/SYNC.md` forbids ("anything that creates accounts or throwaway rows ... never prod"). Before running it, approve and document a narrow exception: one named production test account plus the approved App Review accounts (the same allow-list as the sandbox restriction below), a cleanup procedure that removes the rows afterwards, and an amendment to that `docs/SYNC.md` rule in the same change, so an operator can follow both documents. enable the access-token hook on prod, deploy `revenuecat-webhook` and `delete-account`, set the webhook secret, then verify purchase to sync end to end with a sandbox account on prod, **on both Android and iOS** (EPIC #75 requires sandbox purchases on both stores; one platform's passing proves nothing about the other's purchase path). The webhook accepts only `PRODUCTION` events unless `REVENUECAT_ALLOWED_ENVIRONMENTS` lists `SANDBOX` too (default `PRODUCTION`, `revenuecat-webhook/logic.ts` on #283's branch), so set it for the check. Apple reviews in-app purchases in the sandbox and TestFlight purchases are sandbox too, so taking `SANDBOX` out right after the check would leave the iOS release review unable to create an entitlement: either keep `SANDBOX` accepted through App Review (the cost is that sandbox accounts get real entitlement rows for the window) (a separate staging endpoint is **not** an option: `SUPABASE_URL` is compiled into the binary and TestFlight and the App Store ship the same binary, so a review build pointed at staging would send released users there too, and there is no runtime routing for it), and run the transfer check (#281) inside the same window; remove `SANDBOX` once review has passed. **Sandbox must not revoke a production grant**: if a paying account also makes a sandbox purchase, a later sandbox expiry could overwrite its production entitlement row and stop sync after the next token refresh even while the production subscription is active. A tester who buys in the sandbox on a production-connected build could also get a real entitlement for free, and that grants sync API access even while the release has sync compiled out, so sandbox grants are **restricted to an allow-list of approved test and App Review accounts** (App Review's access is preserved by listing its account). Before `SANDBOX` is enabled, the webhook must keep sandbox and production state apart (a sandbox event never lowers or ends a row a production event wrote), and the rollout checks the mixed-environment case; configure the RevenueCat webhook URL and its authorization header before the purchase. `authorized()` in `revenuecat-webhook/logic.ts` compares the **whole** `Authorization` value to `REVENUECAT_WEBHOOK_SECRET` and does not strip a `Bearer ` prefix, so RevenueCat's header value must be exactly the stored secret (or the secret must be stored with the prefix); a mismatch is a 401 and no entitlement is created.
9. **Transfer decision (#281).** A restore to another account can leave a paying user without sync until renewal when the source has no live mirrored grant. Before the flags move, decide #281 (query RevenueCat for the destination's entitlement instead of copying the source row) or explicitly accept the limitation, and run a restore-to-another-account check next to the purchase checks.
10. **Sign-in providers.** ADR 0019 requires Google, Apple and GitHub. `config.toml` has Apple (disabled) only, so implement and configure each provider in production, then verify a real sign-in with each one: a purchase test through one provider proves nothing about the others.
11. Privacy, data-safety, listing.
12. **Cancellation and expiry.** EPIC #75 requires it: cancelling stops renewal but does not end the current period, so first verify access **continues until the subscription expires** (a refreshed token still syncs), then that the entitlement row ends and sync stops once the entitlement and the token have expired, on both stores, before the flags move.
13. **Release notes.** `.github/workflows/release.yml` (around lines 306–309) always writes "Sync is compiled out" and that no library data leaves the device; flipping the flags without changing that generated text would publish wrong notes for the sync launch, so the same release updates it (the landing never mentions paid features, before or after launch; the Play listing follows its own timing and may describe sync once it ships).
14. **Coordinate the sync-enabled releases.** An iOS app already in the App Store does not mean the sync-enabled iOS build is available when Android launches: the train promotes Play before submitting iOS to App Review, and an iOS hold does not hold Play, so a rejection could leave Android users paying for sync with no iPhone support, against ADR 0019's same-week goal. Plan the promotion together: submit the iOS build for review first, hold Play's promotion of the sync-enabled build until iOS is approved (or release both on the same day), and decide in advance who calls the pause if one side slips (`docs/RELEASING.md`).
15. **Gate on iOS.** ADR 0019 puts iOS in the App Store before the flags move, so Android and iOS gain sync together (#78). Only then flip the release flags, in a dedicated release.

## Hazards
- Merging a `release/*` into `main` applies migrations to **prod** automatically; #283's policies lock everyone out until the hook is on. Harmless only while sync is compiled out of every release, which is why step 7 comes before the flags and not with them.
- #283's migration timestamps must sort after develop's newest at merge time (#727).
- Paid features (sync, co-watch) never appear on the landing, before or after they ship; the Play listing is a separate question and follows its own timing (CLAUDE.md).
