# Discover opens offline

Issue #724.

## Problem
`SearchViewModel.loadDiscover` makes four calls in order (movie genres, TV genres, popular movies, popular TV); any failure sets `error` and the screen is a full-screen `ErrorState`. Only Ktor's in-memory `HttpCache` exists, gone with the process. Detail already falls back to a stored copy; Discover does not.

## Proposal
- **`discoverCache`** table: section key, TMDB language, raw JSON, `fetchedAtEpochMs`. A cache, not user data, same family as `titleWatchProviders`, `episode` and `remoteConfigCache`: no `isDirty`/`updatedAt`/soft delete; absent from `SyncChangeSet`, the export and a restore; wiped by Delete all data. Claim the migration number in `docs/EPICS.md` when the implementation branch opens (AGENTS.md), not at merge.
- **Raw and pre-mute.** Store what TMDB returned, including both genre lists (a genre failure fails the screen today), and apply Muted Genres when reading. A mute change then re-filters cached data instead of showing stale content. Discover reads page 1 only (20 titles) and ADR 0031's live check lost 5 of 20 to the default TV mutes, so a raw page filtered locally can leave a shelf thin. Refill rule: when filtering leaves fewer than 12 titles in a popular shelf, the revalidation reads page 2, then 3 (stop at 3), storing each page raw under the same shelf key; offline, the shelf shows whatever the stored pages leave after filtering. The stored copy comes from an **unfiltered request** (no `without_genres`), and the same response feeds the screen, filtered locally with the refill rule above, so one request serves both the display and the cache. This replaces server-side muting for these shelves, which amends ADR 0031 (its concern was thinning, which the refill rule answers); a genre the user picks with a chip still queries the server with its own filter. Sending `without_genres` and storing that response would make "Show muted" unable to restore titles from the cache.
- **Read path**: emit cached sections immediately; revalidate in the background **only when the stored copy is older than the TTL below** **or no stored copy exists for the section** (first online launch, a language change, a decode failure: a miss has no age to compare, so it fetches at once), or the user refreshes (pull-to-refresh, plus a keyboard-reachable **Refresh** action on the cached screen: pull gestures do not exist with a keyboard or mouse, desktop has no connectivity signal, and the current Retry exists only in the full-screen error state; either one **bypasses `HttpCache`** with a `no-cache` request: `TmdbProvider` otherwise answers a fresh in-memory entry without contacting TMDB, and the database TTL would reset on an unchanged response), or connectivity returns while the copy is stale **or a section has no stored copy** (a missing section has no age, and the existing reconnect retry fires only on a screen error, which a partly cached screen never shows, so the retry is keyed on missing sections too), or a **refill** is due: a change to the mute set or the "Show muted" chip can leave a shelf under 12 titles on a fresh copy, and reading pages 2 and 3 then is a refill, not a revalidation, so the TTL does not hold it back); on success replace the row and the UI; on failure keep that section's cache. A banner "Offline · showing saved" appears only when the data is older than its TTL and the refresh failed. Nothing cached and offline keeps today's error state. A section with no cached copy whose fetch fails is hidden by today's empty-row behavior and would be invisible, so it renders an inline **"Couldn't load" row with Retry** under its real header while the cached sections stay as they are.
- **TTL**: show any age while offline; refresh when older than 6 h (popularity moves daily).
- **For you** is cached too, keyed by its seed set. Today `forYouFlow` turns a failed recommendation request into an empty list, which is indistinguishable from "no recommendations"; the refresh must keep a failure signal (success with a list, or failure) per seed, and a failed seed or section keeps its stored rows. Only a successful refresh, empty or not, replaces them. On every read the stored recommendations are merged and filtered against the **current** library and decided ids (`SearchViewModel` already does this for live results), so a title the user saved, skipped or snoozed meanwhile cannot reappear offline (a snoozed title is not a decided one, and `SearchViewModel` passes the snoozed ids to `forYouFlow` too: the cache read observes all three sets).
- Web uses the same database (SQL.js), so a *loaded* app gets this for free: the claim is limited to an already-loaded app (a reload while offline, a lost connection). Web does not cache its assets, so an offline cold start of the page itself is out of scope here; making it work would need a service worker, tracked separately if wanted.

## Corner cases
Language or region change (key includes language); first run offline; one section fails and three succeed; row growth (one per section, replaced); skeleton must not flash on a cache hit (see `home-skeleton-wave.md`); corrupt JSON after an app update changes the model (decode failure = cache miss, never a crash); `HttpCache` and this cache both answering (one policy: the DB read comes first and the network is asked only once the copy is past its TTL; `HttpCache` stays the in-memory layer under that request).

## Tests
A cached genre chip stays selectable offline but its request can fail, and today that replaces Discover with the full-screen error and hides the genre Back action: a failed genre request keeps the screen, shows an inline error on the genre section only, and keeps Back available. A pull-to-refresh with a fresh `HttpCache` entry reaches TMDB; an online cold start with an empty cache fetches every section; a partly cached screen (one genre section missing, offline) fills the gap when connectivity returns; a mute change on a fresh copy refills a thin shelf immediately; a saved, skipped or snoozed title leaves cached For you; offline cold start renders cached; per-section failure; mute change re-filters; language change misses; decode failure falls through; `ExportShapeTest`, `SyncChangeSetShapeTest` and the eraser cover the table; migration test with the new fixture.
