# Discover opens offline

Issue #724.

## Problem
`SearchViewModel.loadDiscover` makes four calls in order (movie genres, TV genres, popular movies, popular TV); any failure sets `error` and the screen is a full-screen `ErrorState`. Only Ktor's in-memory `HttpCache` exists, gone with the process. Detail already falls back to a stored copy; Discover does not.

## Proposal

> **Historical: the Popular-shelf policy in this section is superseded by ADR 0031 (`docs/adr/0031-muted-genres.md`), which governs.** The Popular shelves request with `without_genres`, store that response, and filter at read only what the person muted. Where this section stores raw Popular pages, sends an unfiltered shelf request, or says server-side muting is replaced, it records the rejected alternative and is not an instruction.
- **Partial seed refresh keeps per-seed freshness.** For you is built from several seeds; if one seed's refresh succeeds and another fails, advancing the section's single `fetchedAtEpochMs` would make the failed seed look fresh and miss the reconnect retry for six hours. The section timestamp advances only when **every** stale seed has refreshed (the old one is kept otherwise, and the row records which seeds are stale), and a partial-failure test covers it.
- **`discoverCache`** table: section key, TMDB language, raw JSON, `fetchedAtEpochMs`. A cache, not user data, same family as `titleWatchProviders`, `episode` and `remoteConfigCache`: no `isDirty`/`updatedAt`/soft delete; absent from `SyncChangeSet`, the export and a restore; wiped by Delete all data. Claim the migration number in `docs/EPICS.md` when the implementation branch opens (AGENTS.md), not at merge.
- **Raw storage for the genre lists.** Store what TMDB returned for both genre lists, so a genre failure is handled per section (today it fails the screen).
- **Popular shelves (historical, superseded by ADR 0031).** The rejected policy stored raw Popular pages, sent an unfiltered shelf request, and replaced server-side muting with client filtering. What stands: the shelf requests carry the muted genres in force and store each response, and a chip-picked genre still queries the server with its own filter. Completeness is decided in `DiscoverFeed.popularShelf` and `DiscoverFeed.needsRefresh`, not restated here.
- **Read path**: emit cached sections immediately, **after the first muting value arrives** (`SearchViewModel` waits for it, as ADR 0031 requires, so nothing is shown unmuted). Refreshes bypass `HttpCache` with a `no-cache` request, because `TmdbProvider` otherwise answers a fresh in-memory entry without contacting TMDB, and the database TTL would reset on an unchanged response. A section with no cached copy whose fetch fails renders an inline **"Couldn't load" row with Retry** under its real header while the cached sections stay as they are. Nothing cached and offline keeps today's error state. When a refresh runs is decided in `SearchViewModel` and `DiscoverFeed.needsRefresh`, not restated here.
- **TTL**: `DiscoverFeed.TTL_MS` (6 h). When a refresh runs is decided in `DiscoverFeed.needsRefresh`, not restated here.
- **For you** is cached too, keyed by its seed set. Today `forYouFlow` turns a failed recommendation request into an empty list, which is indistinguishable from "no recommendations"; the refresh must keep a failure signal (success with a list, or failure) per seed, and a failed seed or section keeps its stored rows. Only a successful refresh, empty or not, replaces them. On every read the stored recommendations are merged and filtered against the **current** library and decided ids (`SearchViewModel` already does this for live results), so a title the user saved, skipped or snoozed meanwhile cannot reappear offline (a snoozed title is not a decided one, and `SearchViewModel` passes the snoozed ids to `forYouFlow` too: the cache read observes all three sets).
- Web uses the same database (SQL.js), so a *loaded* app gets this for free: the claim is limited to an already-loaded app (a reload while offline, a lost connection). Web does not cache its assets, so an offline cold start of the page itself is out of scope here; making it work would need a service worker, tracked separately if wanted.

## Corner cases
Language or region change (key includes language); first run offline; one section fails and three succeed; row growth (one per section, replaced); skeleton must not flash on a cache hit (see `home-skeleton-wave.md`); corrupt JSON after an app update changes the model (decode failure = cache miss, never a crash); `HttpCache` and this cache both answering (one policy: the DB read comes first; `HttpCache` stays the in-memory layer under the network request).

## Tests
Not covered, tracked in #835: a title cached before its genre was muted, shown after an offline unmute with no network fetch, has no test under the chosen design (ADR 0031). `a_cancelled_forced_refresh_leaves_the_unmuted_genre_owed_on_the_next_reload` pins only that a refresh is owed. A cached genre chip stays selectable offline but its request can fail, and today that replaces Discover with the full-screen error and hides the genre Back action: a failed genre request keeps the screen, shows an inline error on the genre section only, and keeps Back available. A pull-to-refresh with a fresh `HttpCache` entry reaches TMDB; an online cold start with an empty cache fetches every section; a partly cached screen (one genre section missing, offline) fills the gap when connectivity returns; a saved, skipped or snoozed title leaves cached For you; offline cold start renders cached; per-section failure; mute change re-filters; language change misses; decode failure falls through; `ExportShapeTest`, `SyncChangeSetShapeTest` and the eraser cover the table; migration test with the new fixture.
