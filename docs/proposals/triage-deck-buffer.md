# Triage: a deck that is rarely empty

Issue #722. Follow-up to #183 (its "persist the cursor" option was never built).

## Problem
Users with many decided titles reach an empty deck, a spinner or "Keep looking". From reading the code (not reproduced):
1. Every swipe at ≤3 cards calls `refill`, which starts with `loadJob?.cancel()`. The cursor moves only when a whole `loadDeck` returns, so for a user whose batch costs up to five sequential `/discover` calls the refill is killed before it lands.
2. `DeckCursor` is a ViewModel field: each visit restarts at page 1.
3. `DeckLoader.load` gathers whole 20-title pages and returns `merged.take(wanted)`. The cursor has moved past the rest and `shown` never learned them.
4. Batch 10 / threshold 3 / the stop rule counts empty batches, not pages.

## Proposal
- **One refill at a time.** A swipe never cancels. Reset (type/genre/mute change, retry) cancels with a generation token so a late result is dropped.
- **Buffer**: low-water 5, target 10. Append each batch on arrival. Budget by pages read per refill, not by empty batches.
- **Keep the overflow** as a queue behind `cards`, drained before any network call.
- **Due Snoozes stay a separate source.** Both the initial read and each per-batch read exclude only Snoozes that are **not due** (`LoadDeckUseCase` passes due ones as the second source); excluding every Snooze would filter due ones out before they enter the deck. A test with a due Snooze covers the initial and a later batch. **A queued card can go stale after it enters the deck**: a sync may add its title, the user then decides it and Undoes, and `UndoDecisionUseCase` would clear progress and remove the collection entry that the sync created. So exclusions are re-checked **when the user acts** (a card whose title is now in the library or decided is dropped, not recorded), and Undo reverses only what that decision itself wrote (the same created-by-this-action rule as ADR 0037), never state a concurrent sync produced. A test syncs a title after it enters the deck, decides it and Undoes, and asserts the synced state survives.
- **Read the exclusion set once per refill** (decided ids, library, snoozes) instead of once per batch.
- **The checkpoint trails durability.** `TriageViewModel.onDecide` removes the card before `actions.record` persists the decision (Snooze the same), so `resumePage` advances only past pages whose cards' decisions or Snoozes are written: a card stays pending for checkpoint purposes until then. Otherwise process death between the swipe and the write loses the decision and resumes more than two pages past the card. A recovery test stops between those two writes. **Undo is crash-safe the other way**: when an Undo makes a card pending again, the checkpoint moves back to that card's page first and the Undo becomes durable only after, so process death between the two cannot skip the card until the next page-1 walk. A second recovery test stops between those writes. **A due Snooze has no Discover page to rewind to**: it enters through the second source, so when the user snoozes it again and then undoes that Snooze, `UnsnoozeUseCase` removes the row. Undo therefore restores the **original due Snooze** (due date and card snapshot as they were) before the Undo is durable, rather than deleting it, so the card returns after process death; a third recovery test covers it. **Exclusions are re-checked when a card is offered, not only when the refill read them**: a sync that adds a title after the refill read its exclusion set must not let a later batch offer it, since a save followed by Undo of the verdict could clear progress and remove the existing library entry. Each batch is filtered against a fresh exclusion read before its cards enter the deck, and a test syncs a title in between two batches. A refill never injects a card that is already in the deck or the overflow queue, including one an Undo has just returned (`onUndo` removes its id from `shown`, so a refill reading after the restore could otherwise add it again): the refill excludes ids present in the deck and the overflow, and a test runs Undo during an in-flight refill.
- **A restored decision invalidates cursors.** The Skipped screen can restore a decision and make its title eligible again; a saved `exhausted` cursor would then report "All caught up" instead of finding it. Removing an exclusion (restore of a decision, Unsnooze) clears `exhausted` and rewinds to `resumePage` for every cursor, and a test restores after exhaustion.
- **Persist the cursor per device.** Key: type + genre + mute fingerprint + TMDB language. Value, per type: `nextPage`, `exhausted` (today's `DeckCursor` tracks it separately from the page), the earliest page that still holds a card the user has not acted on (`resumePage`), and `savedAt`, which is **anchored to the start of each page-1 walk and preserved across checkpoints**: refreshing it at every checkpoint would let repeated visits inside 24 hours keep a cursor alive past the point ranking drift makes it unsafe. When no card is pending (a fully decided batch can advance `nextPage` without producing one) `resumePage` is `nextPage`, and an `exhausted` type stays exhausted until the TTL sends it back to page 1. **Exception:** when the last page held unacted cards, the saved `exhausted` flag is cleared on restore, because the resume rewinds onto those pages and `DeckLoader` would otherwise refuse to read them; it is set again when the last page is read again. **TTL 24 h; resume two pages before `resumePage`; older → page 1.** A batch can span five pages, so "two before the next page" would skip cards from the first pages of a batch the user never reached before the process died; checkpointing the earliest page with an unacted card cannot. Re-reading is cheap and safe: decided ids are excluded on the way in. **The guarantee is best effort**: it holds while the ranking is stable. If drift moves an unacted title from page 100 to page 97 and the resume lands at 98, it is skipped until the TTL runs out or the next page-1 walk. If exact recovery were required, the pending cards (about ten rows: id, title, year, poster, overview) would be persisted instead; not worth a table today.

## Why 24 h and a rewind
TMDB documents popularity as a "lifetime" score built from daily counts (views, votes, favorites, watchlist adds, the previous day's score). It publishes no recompute schedule, so treat the order as moving daily: a title can climb above the saved page and be skipped. Rewinding two pages absorbs small drift; the TTL bounds the rest. Discover stops at page 500 (a TMDB support answer, not the API reference, which states no maximum), so the stored value is the *next* page to read: a cursor of 500 still has page 500 to read, and the catalogue is exhausted only after the last available page has been read: `min(totalPages, 500)` from the response (a filtered result can have fewer than 500 pages), which is what `DeckLoader` does today with `page >= totalPages`. A cursor at 500 with `totalPages` of 500 still has page 500 to read.

## Corner cases
Reset mid-refill; process death; two filter keys with different cursors; offline (keep the deck, no spinner while cards remain); Snooze injection never replaces a card already displayed at the top (the existing `SnoozePlacement.FIRST` and `MIXED_IN`-with-no-fresh-cards cases, which deliberately put due Snoozes first, are unchanged); undo of a verdict returns the card to the front; deck seeded from Next Pick (#554/#555) bypasses the cursor.
