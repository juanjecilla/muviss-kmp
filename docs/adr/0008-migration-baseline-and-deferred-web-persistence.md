# Migration baseline; web persistence deferred behind a failing driver

Two EPIC 10 ("platform data parity") decisions worth recording:

**Migration baseline.** `AppSettings.sq` / `CollectionEntry.sq` / `EpisodeProgress.sq` / `Profile.sq` grew additively with no `.sqm` files through EPICs 0-8 — every install so far always created the database fresh from whatever the `.sq` files currently declared; there was never an upgrade path to test. Rather than synthesize a history that never happened, those four files **as they stand today are declared schema version 1**, with no migration file needed to represent it. `verifyMigrations` is turned on in `core/database/build.gradle.kts` from this point forward, checked against a generated schema fixture (`core/database/src/commonMain/sqldelight/databases/1.db`) — the SQLDelight Gradle plugin wires the resulting `verifyCommonMainMuvissDatabaseMigration` task into `check` (and so into CI) automatically. Any future change to a `CREATE TABLE` that existing installs must pick up without losing data now has to ship as a new `<version>.sqm` file alongside the `.sq` change, or this task fails the build.

**Web persistence stays deferred, on purpose.** SQLDelight's only maintained browser driver, `web-worker-driver`, does publish for both `js` and `wasmJs` (confirmed via Maven Central's Gradle module metadata — the epic that requested this work suspected wasm support might be missing; it isn't). It wasn't wired anyway, because that driver talks to a Web Worker over `postMessage` and is therefore inherently asynchronous. Using it requires flipping SQLDelight's `generateAsync` option on for the database — a property scoped to the whole `sqldelight { databases { create("MuvissDatabase") { ... } } }` block, with no per-target toggle, since every target (Android/iOS/JVM/JS/Wasm) shares the one `commonMain` schema. Turning it on would turn every generated `*Queries` method into a `suspend` call on *every* platform, not just web, forcing every `feature:*:data` repository (collection, progress, profile, settings) onto suspend-based queries across the board. That's a cross-cutting migration of the whole data layer, not a driver-wiring task, and doing it inside this epic risked regressing the already-shipped, synchronous Android v1.

Decision: defer. `DatabaseDriverFactory` on `js`/`wasmJs` (`core/database/src/webMain/kotlin/.../DatabaseFactory.web.kt`) returns a driver that constructs successfully — so Koin can build the object graph and the app doesn't crash at startup or at screen-navigation time — but throws the first time any query actually runs. Every screen that reads from the database drives that read through a ViewModel `Flow` with `.catch { }` (`CollectionViewModel`, `ProgressViewModel`, `ProfileViewModel`, `SettingsViewModel`), so the failure surfaces as a normal error state instead of an uncaught exception. (Before this decision, the previous "just throw from `create()`" stub actually crashed the app the moment any of those screens built their Koin object graph — the throw happened during dependency resolution, before any `Flow` existed to catch it. The failing-driver approach fixes that without implementing real persistence.)

The real fix, whenever it's picked up, is one of: (a) do the whole-app async migration, or (b) give web its own second SQLDelight schema/module (`generateAsync = true`, scoped only to `js`/`wasmJs` source sets) with web-specific repository implementations, trading duplicated schema/repos for not touching the synchronous native path at all.

## Amendment (2026-07-16, EPIC 13): web persistence shipped — path (a), whole-app async migration

The deferred work above was picked up and finished. Decision was path (a) from the original "real fix" list: the whole-app `generateAsync` migration, not a second web-only schema. It turned out to be far more mechanical than the original risk assessment feared, **plus** real web persistence (path b's driver-wiring) landed in the same pass, because the mechanical fallout was small enough to leave time for it. Both are live on `main` now.

**Why it was mechanical.** The fear driving the original deferral was that `generateAsync` would force suspend calls onto Android/iOS/JVM's read path too. It doesn't, in practice:

- Every mutating query (`INSERT`/`UPDATE`/`DELETE`) becomes a real `suspend fun` on the generated `*Queries` classes — but every mutation method on every `feature:*:domain` repository interface (`CollectionRepository.setFavorite`, `ProgressRepository.setSeen`, etc.) was **already** `suspend` before this change, for the obvious reason that writing to a database is a suspend-shaped operation. So the suspend-ness doesn't leak anywhere new at the interface level — only the *bodies* of `feature:*:data` repositories needed touching (propagating `suspend` onto a couple of private helper functions that got called from an `init` block or a bare private `fun`, plus `queries.transaction { }`'s block type, which SQLDelight's generated `SuspendingTransacterImpl` already made suspend-lambda-shaped automatically).
- Select queries (`Query<T>.executeAsList()`/`executeAsOneOrNull()`/etc.) are **untouched** by `generateAsync` — `Query.execute()` just forwards to whatever `driver.executeQuery(...)` returns, and that stays `QueryResult.Value` (synchronous) for every sync driver regardless of the flag. The only reason to touch a call site was genuine web correctness: `executeAsList()` calls `.value` synchronously, which throws on the real web driver's `QueryResult.AsyncValue` (see `QueryResult.DefaultImpls.getValue`, which throws `IllegalStateException` with a message pointing at `generateAsync` — this is SQLDelight's own designed guard rail, not a bug). Those handful of call sites (`SqlDelightCollectionRepository.upsertSnapshot`, `SqlDelightListsRepository.addEntry`, `SqlDelightSettingsRepository.exportData`) were switched to the suspend `awaitAsList()`/`awaitAsOneOrNull()` extensions from the new `app.cash.sqldelight:async-extensions` dependency.
- `MuvissDatabase.Schema` changed type from `SqlSchema<QueryResult.Value<Unit>>` to `SqlSchema<QueryResult.AsyncValue<Unit>>`, which does NOT type-check directly against `AndroidSqliteDriver`/`NativeSqliteDriver` (both still want the synchronous shape — the exact "expect/actual driver factories fighting suspend creation" risk flagged in the original spike plan). `async-extensions` ships the fix for exactly this: `SqlSchema<QueryResult.AsyncValue<Unit>>.synchronous(): SqlSchema<QueryResult.Value<Unit>>`, an extension built for precisely this situation. `DatabaseFactory.android.kt`, `.ios.kt`, and `.jvm.kt` all now do `MuvissDatabase.Schema.synchronous()` before handing the schema to their driver constructors — one-line change per platform, everything else about those files is unchanged.
- The one repeated pattern that needed real (if small) redesign: `SqlDelightProfileRepository` and `SqlDelightSettingsRepository` used to call `queries.ensureRow()` once from `init { }` to guarantee their singleton row existed before any read. `ensureRow` is generated as `suspend fun` too now (it's an `INSERT OR IGNORE`), and `init { }` blocks can't call suspend functions. Fixed by calling the (idempotent) `ensureRow()` from both `observeX().onStart { }` and the top of every mutating method, rather than once at construction.

**The web driver.** `DatabaseFactory.web.kt` (`core/database/src/webMain`) now backs `DatabaseDriverFactory.create()` with SQLDelight's `web-worker-driver`, talking to a Web Worker running `@cashapp/sqldelight-sqljs-worker` (SQL.js — SQLite compiled to wasm) over `postMessage`. `create()` itself stays synchronous (spawning a `Worker` is fire-and-forget from JS's point of view) — a small wrapper, `SchemaEnsuringDriver`, defers the one genuinely-async step (running `MuvissDatabase.Schema` against the worker) to the first real query via a `Mutex`-guarded lazy suspend init, so `DatabaseDriverFactory.create()`'s signature never had to become suspend and Koin's `single { createDatabase(get()) }` wiring is untouched on every platform including web.

**Scope cut: session-only, not durable across reloads.** SQL.js keeps the database in the worker's memory only — there is no OPFS or IndexedDB-backed persistence wired up. A full page reload starts from an empty database again. This was a deliberate v1 cut, not an oversight: `web-worker-driver`'s OPFS support is newer and thinner in the ecosystem, and getting *some* real read/write persistence for the session shipped was judged more valuable than blocking the whole epic on durable storage. Durable web persistence (OPFS, or an IndexedDB snapshot-on-unload/restore-on-load shim) is the natural EPIC 13 follow-up.

**The two genuine non-mechanical snags, and how they were resolved** (documented in detail because they were the two places this could plausibly have gone the "revert" route the original spike plan allowed for):

1. *Webpack didn't bundle the worker's own dependencies.* The documented SQLDelight pattern for referencing the worker script is `Worker(js("""new URL("@cashapp/sqldelight-sqljs-worker/sqljs.worker.js", import.meta.url)"""))`built across two separate calls. That compiles fine and even produces a webpack asset for the worker script — but only via webpack's *generic* `new URL(...)` → static-asset-copy handling, not its native Worker-chunking (`WorkerPlugin`), which only pattern-matches the literal combined expression `new Worker(new URL(...), options)` appearing together. Split across two Kotlin calls, the combined shape never appears in the emitted JS, so webpack copied the worker file byte-for-byte without bundling *its* import of `sql.js` — leaving a bare `import initSqlJs from "sql.js"` that browsers cannot resolve (bare specifiers require either a bundler or an import map). Symptom in a live browser check: the worker loaded (200 OK, confirmed via server logs and the browser's own network log) but every query hung forever with **no console error at all**, because the failure happened inside the worker's own module-loading step, invisible to the main thread. Fix: write the whole `new Worker(new URL(...), { type: "module" })` expression as one untouched `js(...)` string in a single top-level function (`sqljsWorker()` in `DatabaseFactory.web.kt`), preserving the exact AST shape webpack's plugin looks for. `{ type: "module" }` is also required on its own merits — the worker source is an ES module (top-level `import`), which a classic (non-module) Worker cannot parse at all.
2. *sql.js's loader references Node built-ins webpack 5 no longer auto-polyfills.* Once the worker's dependency graph was actually being bundled (confirming fix #1 worked), the build failed instead of hanging: `sql.js/dist/sql-wasm.js` is written to run in both Node and the browser, and unconditionally references `fs`/`path`/`crypto` for its Node code path — a path this browser-only build never takes at runtime, but webpack 5 still needs to *resolve* at build time. Fixed with `app/webApp/webpack.config.d/copy-sqljs-wasm.js` setting `resolve.fallback: { fs: false, path: false, crypto: false }`, webpack 5's documented way to say "this reference is genuinely unused here, don't error on it." The same file also adds a `CopyWebpackPlugin` pattern copying `sql.js/dist/sql-wasm.wasm` (SQL.js's own compiled-to-wasm SQLite binary — separate from the two Kotlin/Wasm-compiled `.wasm` binaries `webApp`/`skiko` already ship) to the output root, because the worker's `locateFile` hook fetches it from an absolute `/sql-wasm.wasm` path that only webpack's asset-copying (not its `new URL()` bundling) can satisfy.

Both were caught by an actual `wasmJsBrowserDistribution` build plus a live browser check (serving the `dist/` output locally, driving the Settings screen, reading console/network logs) — neither would have been visible from a clean compile or a passing `jvmTest` run. That live-browser step is what turned this from "looks done" into actually done; anyone repeating a browser-persistence spike on this codebase should budget for it up front rather than treating a green build as sufficient signal.

New dependencies: `app.cash.sqldelight:async-extensions` (all platforms, `core/database` `commonMain`), `app.cash.sqldelight:web-worker-driver` + `org.jetbrains.kotlinx:kotlinx-browser` (js/wasmJs only — `kotlinx-browser` supplies the `Worker`/DOM external declarations now that Kotlin/Wasm no longer ships `org.w3c.dom` in its stdlib), plus the npm packages `sql.js`, `@cashapp/sqldelight-sqljs-worker`, and the dev-only `copy-webpack-plugin`.

## Amendment (2026-08-27): `webMain` is a compilation, not just a directory

`./gradlew build` had been failing at `:core:database:compileWebMainKotlinMetadata` with `Unresolved reference 'WebWorkerDriver'` since the amendment above landed, while every CI step stayed green. Two things had been mis-recorded and are corrected here.

**1. `webMain` is a real source set with its own compilation.** A previous note in `core/database/build.gradle.kts` claimed the project's `sourceSets` container had no source set named `webMain` ("confirmed empirically: it is absent from `kotlin.sourceSets.names`"), and hung the web dependencies on `jsMain` and `wasmJsMain` twice instead. What is actually true is narrower: `webMain` is created by the default hierarchy template *after* the module's own `kotlin { sourceSets { } }` block runs, so `val webMain by getting` throws at configuration time — but by the time the build graph is assembled it exists, along with `compileWebMainKotlinMetadata`, which type-checks `src/webMain/kotlin` once, ahead of and independently of either target, against `webMain`'s own dependencies. Declaring the klibs per target left that compilation with nothing to resolve against. They are now declared on `webMain` via `matching { it.name == "webMain" }.configureEach { }` (lazy, so it also applies to elements created later) and both targets inherit them. `npm(...)` stays per target — it feeds each target's webpack/yarn resolution and means nothing to a metadata compilation.

**2. The `DatabaseDriverFactory` actual cannot be shared, after all.** It was in `webMain` as `DatabaseFactory.web.kt`. It cannot be: `WebWorkerDriver`'s parameter is `expect class app.cash.sqldelight.driver.worker.expected.Worker`, and a shared source set can name neither resolution of it — `org.w3c.dom.Worker` fails the metadata compilation (`actual type is 'org.w3c.dom.Worker', but 'app.cash.sqldelight.driver.worker.expected.Worker' was expected`; a metadata compilation cannot see through an expect class to its actual), and `expected.Worker` fails `compileKotlinWasmJs` (`Cannot access 'typealias Worker = Worker': it is internal in file` — the wasmJs actual typealias is internal to the library). The library's own `createDefaultWebWorkerDriver()` is not an escape hatch either: its js actual builds the URL and the `Worker` in two separate calls, precisely the shape that defeats webpack's worker bundling (snag 1 above), and neither actual passes `{ type: "module" }`.

So the file was split the way `DataExporter` already is: `DatabaseFactory.js.kt` and `DatabaseFactory.wasmJs.kt` hold the eight-line actual and `sqljsWorker()` per target, and `webMain` keeps `SchemaEnsuringDriver.kt`, which needs only `SqlDriver` and compiles shared as intended.

**Why CI missed it.** CI compiled `compileKotlinJs compileKotlinWasmJs`, which read `src/webMain/kotlin` straight into each target and never ran the metadata compilation. Every intermediate source set in the repo was uncovered the same way (`appleMain`, `iosMain`, `nativeMain` included). CI now also runs `allMetadataJar`, which compiles each of them; it needs no Kotlin/Native toolchain, so it runs on `ubuntu-latest` alongside the rest.

## Amendment (2026-09-04, EPIC 24): web persistence is durable — a forked worker and an IndexedDB snapshot

The "scope cut: session-only, not durable across reloads" above is lifted. A page reload now keeps the user's library, and `triageDecision` — whose entire promise is not asking about the same title twice — survives with it. This was issue #28.

**There was no seam to configure.** `@cashapp/sqldelight-sqljs-worker/sqljs.worker.js` is sixty lines and does `db = new SQL.Database()` unconditionally. No `export()`, no load-from-bytes, no VFS, no option. So durable storage could not be reached by wiring the driver differently, and the choice was never "OPFS or IndexedDB" — it was "which worker do we ship". `WebWorkerDriver` speaks only a `postMessage` protocol (`exec` / `begin_transaction` / `end_transaction` / `rollback_transaction`, replying `{ id, results }` or `{ id, error }`), so anything answering that protocol is a valid worker. Ours is `core/database/src/webWorker/muviss-sqljs.worker.js`, a fork of those sixty lines.

It is declared as a **local npm package**, not a file in resources, and that is load-bearing: `new URL("muviss-sqljs-worker/muviss-sqljs.worker.js", import.meta.url)` has to resolve through `node_modules` for webpack to bundle the worker's own `import initSqlJs from "sql.js"` along with it. A path reference gets the verbatim-copy treatment that is snag 1 above, and presents as a worker that loads with a 200 and then hangs forever with no console error.

**What it does.** On start it opens IndexedDB (one store, one key), and hands the bytes to `new SQL.Database(bytes)` when they are there. After any mutating `exec` and after every `end_transaction` it marks the database dirty and, ~500ms after the last such write, exports the whole database and puts it back. The main thread posts a `flush` action on `pagehide`, since a worker cannot observe the page going away — it is simply terminated.

**Chosen against OPFS**, via `@sqlite.org/sqlite-wasm`, which would give real incremental durability and no loss window at all. Rejected for this pass because it means a new wasm asset, new webpack asset rules and a worker written from scratch, discarding both hard-won fixes above — and because its `opfs-sahpool` VFS (the only one available to us, since GitHub Pages cannot send the COOP/COEP headers the plain `opfs` VFS needs) takes an exclusive handle, so the *second* tab fails to open the database at all. It is not better on multi-tab, only differently bad.

The costs of the snapshot approach, stated plainly so the trigger to revisit is legible: `db.export()` serializes the **entire** database on every committed burst, which is O(size) per write and fine for a personal library of a few hundred titles and not fine for something an order of magnitude larger; and there is a **loss window** of up to the debounce interval if the tab dies without `pagehide` running. If either becomes real, OPFS is the answer and this paragraph is why.

**Multi-tab is decided, not ignored.** Two tabs are two workers with two independent in-memory databases and one IndexedDB slot, so the naive version has the second tab's export silently overwrite the first tab's work wholesale — the same class of silent data loss ADR 0013 exists to prevent, reached from a different direction. The worker takes a Web Lock (`navigator.locks.request("muviss-db")`) held for the life of the tab: the holder persists, other tabs run normally in memory and never write. The loser tab's changes are lost on reload, which is exactly what *every* tab did before this amendment, so it is not a regression — and data that is already durable can never be clobbered by a stale tab. Telling that tab so, in the UI, is deliberately not done here. *(Two claims in this paragraph are wrong: the lock request queues rather than refusing, so durable data **can** be clobbered by a stale tab; and the tab is told now. See the 2026-09-05 amendment.)*

**`SchemaEnsuringDriver` now decides rather than creates.** It called `Schema.awaitCreate` unconditionally, which was only correct because web's database was empty on every load. A restored snapshot can be older than the build, so it reads `PRAGMA user_version` and creates (0), migrates (below the target) or does nothing. Web has never had an upgrade path because it never had a stored database; this is the one every other platform gets free from its driver, and it means the `.sqm` chain and `verifyMigrations` finally cover web rather than covering it vacuously. A database *newer* than the build is left alone rather than recreated — someone opening a stale deployment should not have their library deleted to fix a version number. The target comes from `MuvissDatabase.Schema.version`, never a literal, so the next `.sqm` moves it without anyone editing the driver.

## Amendment (2026-09-05, issue #53): the losing tab is told, and `ifAvailable` is not the fix it looks like

**"Telling that tab so, in the UI, is deliberately not done here" no longer holds.** A tab that is not the writer now says so.

The worker posts `{ writer, supported }` when the election resolves and when Web Locks is absent, over a **`MessageChannel` of its own**. The first attempt shared the worker's existing message channel with SQLDelight's driver, on the strength of reading the **js** `web-worker-driver` klib, where `WorkerWrapper.execute` adds a per-request listener that compares `event.data.id` and ignores what it does not recognise. The **wasmJs** driver is a different implementation: `WasmWorkerResponse.results` is a non-null external property, materialised *before* the id is looked at, so an extra message with no `results` took the whole app down —

```
NullPointerException: null
  at ...WasmWorkerResultWithRowCount.<init>
  at ...results_$external_prop_getter__externalAdapter
```

— on the second tab, at the exact moment the banner appeared. Sharing `webMain` does not mean sharing a driver. A private port is not a workaround for that; it is the correct shape, since the driver's protocol is the driver's.

On the Kotlin side the seam is `PersistenceStatus` in `:core:database`, exposed as `DatabaseDriverFactory.persistence` and bound into Koin by `MuvissApp`'s `platformDatabaseModule`. Android, iOS and JVM return `AlwaysDurable`. It is a Koin binding rather than an `expect`/`actual` value for the reason `CLAUDE.md` records about `OAuthRedirectTarget`: a JVM actual hard-coding `Durable` would make the banner impossible to render in a `jvmTest`, which is the only place Compose tests run here.

Four states, and `Pending` earns its place — it is what a tab reports before the election answers, and it draws nothing. Treating "not yet known" as "not durable" would flash the banner on every ordinary load of the writer tab. `NotPersisted` (no Web Locks at all, so nobody is elected and nothing persists anywhere) says something different from `ReadOnlyTab` on purpose: "open in another tab" would be a lie when there may be no other tab.

Because a queued lock request is simply *silent* until granted, the losing tab is told by a timer: `ELECTION_GRACE_MS` (400ms) after requesting, if it still is not the writer, it announces. The delay is what keeps the winner — granted within a few milliseconds — from flashing the banner on the way in.

### `{ ifAvailable: true }` was tried, and is a worse bug

The 2026-09-04 amendment claimed the lock means durable data "can never be clobbered by a stale tab". That is **false**, and remains false: `navigator.locks.request(name, callback)` **queues**. A losing tab is not refused, it is waiting; when the writer's tab closes it is granted the lock and exports a database forked from the snapshot as it stood when *it* opened, over everything the writer committed in between. That bug is real and is filed separately.

`{ ifAvailable: true }` is the obvious fix and it was implemented, tested in a browser, and **reverted**. On an ordinary page reload the new worker starts before the outgoing one has been torn down, asks while the lock is still held by a tab that is already dying, is refused — and never asks again. Measured in Chrome: one tab, reloaded once, no other tab open, showing the "open in another tab" banner, with `navigator.locks.query()` reporting one holder and zero pending. A user who reloads would silently stop persisting, permanently. That is far more common than two tabs plus closing the writer, so the trade is bad in both directions of frequency and severity.

Whatever fixes the clobber has to keep the reload case working — retrying `ifAvailable` while the tab has no local writes, or re-reading the snapshot on promotion before enabling exports. Neither belongs in a UI change, so the queue stays and the bug is filed with this analysis attached.

### Correction to the 2026-07-16 amendment: `{ type: "module" }` is not what makes this work

That amendment says, of the worker construction:

> `{ type: "module" }` is also required on its own merits — the worker source is an ES module (top-level `import`), which a classic (non-module) Worker cannot parse at all.

**That is wrong**, and it matters now that we own the worker. Reading the built output (`app/webApp/build/dist/wasmJs/productionExecutable/webApp.js`), webpack rewrites the construction to:

```js
new Worker(new URL(r.p+r.u(873), r.b), {type: void 0})
```

`{type: void 0}` — the module type never reaches the browser. Webpack emits a *classic* worker chunk (`873.js`) that pulls its dependencies in with `importScripts`, and the ESM `import` in the source is bundled away before it ever runs. This is why the vendored worker's `if (typeof importScripts === "function")` guard fires at all: `importScripts` is undefined in a real module worker, and had the type actually been applied, that worker would have installed no message handler and every query would have hung.

The rest of that paragraph stands and is the load-bearing part: the whole `new Worker(new URL(...), options)` expression must appear as one untouched `js(...)` string, because webpack's `WorkerPlugin` pattern-matches that exact shape. `{ type: "module" }` is kept for shape parity, not for its stated effect. Our worker is written as a classic worker accordingly.
